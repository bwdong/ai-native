01

CLAUDE.md

项目记忆 · 默认上下文

它是什么

CLAUDE.md 是会话开始时自动读入上下文的纯 Markdown —— 不会被执行、不会被渲染，只是「贴在模型眼前」的项目说明书。

定位是「告诉模型那些代码看不出、但又频繁影响决策」的事实：技术栈、命名陷阱、编码约定、不要碰的坑。 和 README 的差别 —— README 写给人看，可以铺陈；CLAUDE.md 写给模型看，每一行都占上下文 token， 必须精炼到「删掉就会出事」的程度。

分层与生效顺序

CLAUDE.md 支持多级放置，按「从近到远」叠加合并。越靠近当前工作文件的层级，优先级越高：

L1 · 子目录
{repo}/sub/dir/CLAUDE.md —— 局部规则。例如「本目录全是前端代码，约束 React 风格」。只对该目录及子目录生效。
L2 · 项目根
{repo}/CLAUDE.md —— 项目级总约定。本项目就是这一层，声明 GBK 编码、双架构入口、固化拼写错误等。
L3 · 用户全局
~/.claude/CLAUDE.md —— 跨项目个人偏好。例如「回答用中文」「commit 信息用祈使句」。

合并是叠加而非覆盖。出现冲突时通常以更近层级为准，但不保证强语义 —— 所以不要写「L3 说要做 X，L2 偷偷反例外」这种依赖优先级的写法，规则要在合适层级一次写清。

▎ 作用
  • 固化项目级常识，省去每次重复解释
  • 声明禁止 / 必须的硬规则（本项目「禁止修改已有中文注释」）
  • 记录已固化的拼写错误，防止 AI 好心改错（如 parallelFristMap）
  • 提供常用命令速查 —— 构建、单模块编译、跑测试
  • 标明「走哪条路」 —— 双架构 / 历史包袱场景的明确指向
▎ 何时添加
  • 新项目接入 Claude Code 的第一件事（哪怕只写 10 行）
  • AI 反复犯同一个项目特定的错误 —— 写进来就不会再犯
  • 团队约定非显而易见，比如源码非 UTF-8、模块有不寻常的依赖方向
  • 存在「看起来对、做起来错」的坑（拼写陷阱、过时 API、废弃路径）
  • 有双轨/迁移状态，需要明确「新代码走哪条」
▎ 注意事项
  • 每行都占上下文 token，控制在 ~200 行内最佳
  • 只写非显而易见的事 —— 代码 / 文件名能看出的不要重复
  • 用祈使句：「禁止 X」「必须 Y」 > 「最好不要」「建议」
  • 不要写会过期的内容（在做的需求、临时分支、当周 owner）
  • 定期清理：规则一旦内化进代码或工具，就从 CLAUDE.md 删除
  • 不要堆背景故事，那是 README 的活
  • 规则之间避免互相打架；分层写清，不要靠优先级硬猜

写得好 vs 写得差

✓ 好的 CLAUDE.md 条目
- 源文件编码 GBK，禁止用 UTF-8 写中文注释
- 已固化拼写：parallelFristMap、acessControlFilter，禁止改正
- 新增楼层只走 /entrance/finishCommonInfo.action + DUCC，禁止写 Java 代码
- 构建：mvn -pl payfinish-rpc -am compile
✦ 每条都是看代码看不出、改错就出事的硬事实，祈使句 + 可执行，模型能直接照做。
✗ 应该删掉的条目
- 本项目是一个支付完成页系统，负责……（README 内容）
- 我们最近正在做 AI Native 改造，预计 Q3 完成
- 代码风格请遵循阿里巴巴 Java 开发手册
- Controller 在 web 模块，Service 在 service 模块（看目录就知道）
✦ 背景介绍属于 README；时效性信息会过期；通用规范模型已经知道；目录结构能直接看出来 —— 都是纯浪费 token。
判断口诀 / 反模式：盖住每条问自己「模型看不到这条会出错吗？」 —— 答 会 留下，答 不会 删掉。
把 CLAUDE.md 当「许愿池」（「请认真分析」「请考虑性能」）是典型反模式 —— 那是态度不是知识，只会稀释真正重要的信息。
02

Skills

可复用的工作流模板 · 也叫「同事的遗产」

它是什么

Skill 是带触发描述的可复用工作流，本质是一份带 frontmatter 的 Markdown：当用户请求语义匹配 description 时， Claude 主动加载它，按里面的步骤、检查清单、流程图执行。把一位资深同事的肌肉记忆抽离成文件 —— 他踩过的坑、他面对某类需求时的标准动作，全部沉淀下来。

与 CLAUDE.md 的区别 —— CLAUDE.md 每次都加载，Skill 按需触发， 所以可以做得很厚（含子文件、参考资料）而不污染上下文。

▎ 作用
  • 沉淀多步骤标准动作（TDD、调试、PR 流程、写规格）
  • 用检查清单强制纪律，避免跳步
  • 用触发描述实现「该用的时候自动用」
  • 把项目特定操作（如「新增楼层」）封装成一键工作流
▎ 何时添加
  • 同一类任务做过 3 次以上，每次都要交代相同步骤
  • 有容易跳步的关键流程（先写测试、提交前验证）
  • 项目有独特操作模板（楼层接入、新组件配置）
  • 团队希望标准化某种产出（设计文档、规格书）
  • 某位同事即将离职 / 转岗，得趁早把他的套路抄走 ☕
▎ 注意事项
  • description 是触发的关键：写清「何时用、何时不用」比写功能更重要
  • 避免过度泛化的 description，会被错误触发污染上下文
  • 区分刚性（必须按步骤）和柔性（参考原则）skill
  • 多个 skill 同时匹配时，在 description 里说明优先级
  • 定期回顾：写 skill 的同事真走了之后，没人维护的 skill 会变成新的坑
▎ 行业冷知识
程序员的进化路径，是从「写代码」走到「写规则」、再走到「写 skill」。
于是江湖上有这么一句话 ——
「那些拿了大礼包的同事，其实从未离开你。他们只是变成了 skill，默默陪伴在每一次 Claude 调用里。」
你说，暖不暖心？🍂
—— 据说每个被沉淀下来的工作流背后，都有一个连夜写文档的灵魂。
03

MCP（Model Context Protocol）

外部工具与数据源的标准化接入

它是什么

MCP 是 Anthropic 推出的开放协议，让 Claude 通过统一的客户端-服务器模型调用外部工具与数据： 读数据库、查工单、操作 GitHub、访问内部 API。每个能力由一个 MCP Server 提供，Claude 当作一组 tool 调用 —— 相当于「给模型装外设」，Skills 是写在文件里的步骤，MCP 是真正能联网做事的接口。

▎ 作用
  • 突破本地文件系统边界，读写远端资源
  • 对接企业内部系统（工单、文档、监控、CI）
  • 提供类型化的工具调用，比让 AI 拼 curl 更可靠
  • 多个项目共享同一套外部能力
▎ 何时添加
  • 需要接入企业内部系统 —— DUCC 配置中心、行云部署、JoySpace 文档、工单
  • 有内部 API 希望 AI 直接调用，而非打印命令让人复制
  • 用 Bash + curl 拼接已经足够痛苦，需要类型化封装
  • 多个项目 / 多人共用同一套外部能力
▎ 注意事项
  • 权限边界要清晰：MCP 工具默认拥有相应账号权限，等同放开了「真实操作」
  • 区分只读 vs 写入 server，写入操作建议默认 require approval
  • 每个 MCP server 暴露的 tool 都进 LLM 工具列表，太多会污染选择
  • 不要把能用普通 CLI的事强行 MCP 化，普通 Bash 命令更轻量
  • 注意凭证管理：token、密钥的存放位置和共享方式
常见误区：把 MCP 当万能扩展点。其实它是给「跨进程、有状态、需要凭证」的能力用的； 本地一行 bash 能解决的，不要 MCP。
04

Subagents（子代理）

独立上下文 · 并行 / 隔离 · 专精角色

它是什么

Subagent 是从主对话派生出去的独立 Claude 实例，有自己干净的上下文窗口和受限的工具集。 主代理通过 Agent 工具下发任务、接收摘要 —— 类似把活交给一个「带便签纸来汇报」的下属。

典型预置类型：Explore（只读搜索）、Plan（架构设计）、general-purpose（全能）， 也可以在 .claude/agents/ 里自定义角色。

▎ 作用
  • 保护主上下文：让子代理啃大量文件，只把结论带回
  • 并行化：多个独立任务同时跑（前端+后端+测试）
  • 角色专精：限定工具集 = 限定能干什么
  • 独立判断：不被主对话偏见污染，做客观 review
▎ 何时添加
  • 探索任务预计读 10+ 文件且大部分内容用不上
  • 同时有2 个以上独立子任务可以并行
  • 需要独立第二意见（code review、架构审计）
  • 有角色边界需求（只能读、不能改）
▎ 注意事项
  • 子代理看不到主对话历史，prompt 必须自包含
  • 它的报告 ≠ 实际行为，对写代码类任务一定要 verify
  • 简单查找别派子代理，直接 grep / Read 更快
  • 避免多层嵌套派发，调试链路会极其困难
  • 明确告知读还是写，否则它会自行决定
05

Hooks（钩子）

事件驱动的强制约束

它是什么

Hook 是配置在 settings.json 里的 shell 命令，由 Claude Code harness（外壳进程）在事件发生时执行 —— 不是模型自己执行。常见事件：PreToolUse、PostToolUse、UserPromptSubmit、 Stop、SessionStart。

关键差异 ——CLAUDE.md 是「告诉模型应该怎么做」，Hook 是「不管模型怎么想都会发生」。 想要「保存自动 prettier」「提交前必跑测试」这种确定性行为，必须用 Hook。

▎ 作用
  • 强制规则：拦截危险命令、阻断违规编辑
  • 自动化：保存即格式化、提交前自动验证
  • 注入上下文：会话启动时塞入项目状态、当前 PR 信息
  • 审计：记录所有工具调用到日志
▎ 何时添加
  • 「每次 / 每当 / 之后自动 X」类需求 —— Memory 解决不了
  • 有不能违反的硬规则（如禁止 force push 到 main）
  • 希望降低权限提示频次（PreToolUse 自动 approve 安全命令）
  • 会话开始需要注入动态信息（当前分支状态、未读消息）
▎ 注意事项
  • Hook 是真正运行的 shell，写错会让会话卡死或崩溃
  • 不要做耗时操作：每次工具调用都跑，1s 都嫌长
  • 用退出码沟通：0=放行，非 0=阻断（带 stderr 信息给模型）
  • 路径硬编码风险：hook 在不同机器上要可移植
  • 调试困难：先用 --dry-run 或日志验证，再生效
  • 被 hook 阻断时，模型会看到 stderr —— 写清楚「为什么被拒、怎么改」
红线：不要在 hook 里写「如果检测到敏感信息就 rm -rf」之类的不可逆动作。 Hook 应该报告并阻断，让人来决定后续。

五者对比一览

何时选谁，一眼看清
机制 本质 触发方式 作用域 最适合解决 不适合解决
CLAUDE.md 静态文档 会话启动时自动读入 项目 / 用户全局 项目常识、命名陷阱、必守约定 动态状态、复杂工作流、自动化执行
Skills 按需工作流 语义匹配 description 后调用 用户级 / 插件级 多步标准动作、检查清单、流程纪律 需要联网或调外部 API 的能力
MCP 外部工具协议 模型主动调用 tool 跨会话 / 跨项目 访问 DB、工单、内部 API、远端文档 本地一条命令就能做的事
Subagents 独立 Claude 实例 主代理通过 Agent 工具派发 本次会话临时 大范围探索、并行任务、独立 review 简单查找、需要主对话上下文的任务
Hooks 外壳事件回调 harness 在事件触发时执行 项目 / 用户全局 强制规则、自动格式化、上下文注入 需要模型判断的语义性任务
选型直觉：
· 想让模型「知道」 → CLAUDE.md
· 想让模型「会做」某种流程 → Skill
· 想让模型「能碰到」外部世界 → MCP
· 想让模型「分身」做事 → Subagent
· 想让某事「一定发生」 → Hook
